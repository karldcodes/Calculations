# Calculations

## Endpoints

The API exposes a generic calculation execution endpoint:

`POST /calculations/{name}`

The shape of the request body depends on the selected calculation. Rather than manually maintaining separate OpenAPI definitions for each calculation, the API exposes a metadata endpoint.

`GET /calculations`

This endpoint returns the available calculations and their required request fields. The frontend uses this metadata to dynamically render the form. This keeps the backend as the source of truth and avoids duplicating calculation-specific contracts in both OpenAPI and frontend code.

`GET /swagger`

Interactive API documentation via Swagger UI when ran locally

`GET /health`

Health check URL for container orchestration platforms such as AKS.

## Architecture Summary

The solution was designed to minimise duplication between the frontend and backend by making the backend request models the single source of truth for calculations, validation rules and form definitions.

The backend is implemented as a minimal ASP.NET Core API using a strategy pattern to support multiple calculations. Each calculation implements a shared abstraction and is registered through dependency injection. A calculation factory resolves the appropriate implementation at runtime based on the calculation selected by the user.

Each calculation defines its own request and response models. The request models are decorated with Data Annotation attributes such as Required, Range and Display. These attributes serve multiple purposes:

- Defining the API contract used during deserialisation.
- Providing server-side validation rules.
- Supplying metadata used to generate the frontend forms.

At application startup, the API reflects over the registered calculations and generates a cached collection of calculation metadata. This metadata includes information such as field names, labels, input types and validation hints. The frontend retrieves this metadata through the GET /calculations endpoint and uses it to dynamically construct the user interface.

The frontend is implemented using React, TypeScript and Tailwind CSS. Calculation definitions are retrieved using SWR, providing lightweight caching and preventing unnecessary repeated requests. Rather than maintaining a separate hard-coded form for each calculation, the UI renders inputs dynamically based on the metadata returned by the API. As a result, introducing a new calculation does not require any frontend changes.

When a form is submitted, the frontend serialises the input values into JSON and posts them to the relevant calculation endpoint. The backend deserialises the request into the strongly typed request model for the selected calculation and executes the calculation logic.

Validation is intentionally centralised on the backend to avoid maintaining duplicate validation rules in both applications. Validation failures are returned using ASP.NET Core's ValidationProblem response format, allowing the frontend to display field-level error messages alongside the relevant inputs, while also supporting generic form-level errors.

The API also includes OpenTelemetry instrumentation for logs, traces and metrics, together with CORS configuration to support local development. Source-generated logging has been added around request processing to aid troubleshooting and demonstrate how operational concerns could be addressed in a production environment.

### Precision in Calculations

As the API performs numerical calculations, I chose to use the decimal type for the request model properties, as it provides a high degree of precision and helps avoid the rounding errors that can occur with floating-point types such as double and float. Returned results are also not rounded, ensuring that the full calculated value is preserved

### Containerisation

For this tech test, I chose to use Docker Compose to keep the deployment simple rather than introducing the additional complexity of a full Kubernetes implementation. The Docker Compose configuration builds both the API and frontend applications using the Dockerfiles defined within their respective projects.

The Compose file also provisions Grafana's LGTM stack to demonstrate how logs, metrics and traces generated by the application can be collected, visualised and explored through a single observability platform. This provides a lightweight way to showcase monitoring and troubleshooting capabilities in a local development environment without requiring cloud infrastructure.

### Trade-offs and Future Considerations

One of the design goals of this solution was to make the backend the single source of truth for calculations, validation rules and frontend form definitions. While this reduces duplication between the frontend and backend, it does introduce additional complexity and some limitations.

At present, the request models are responsible for defining the API contract, validation rules and the metadata used to generate the frontend forms. This works well for simple scenarios, but it means that any additional frontend-specific configuration must also be expressed through attributes on the request model. For example, if a new form property needed to be exposed to the frontend, a corresponding attribute would need to be added to the model and included in the metadata generation process.

In a more mature implementation, I would consider separating the frontend form configuration from the validation models. For example, calculations could expose an explicit configuration model describing how the form should be rendered:

```csharp
var field = new FormInput
{
    Name = "Probability A",
    Type = "number",
    // Additional UI-specific configuration
};
```

This would provide greater flexibility and allow the frontend experience to evolve independently of the validation model.

With further evolution, these form definitions could be stored outside of the application entirely, for example within a NoSQL database, with an accompanying administration interface allowing users to configure calculations without requiring a deployment. Depending on the business requirements, the calculation logic itself could potentially be made configurable through a rules engine or domain-specific language using technologies such as ANTLR. However, this would introduce significantly more complexity and would only be justified if there was a clear business need for user-defined calculations.

It is also worth noting that, in a real-world application, I would typically maintain the frontend and backend as separate solutions and repositories. This provides clearer separation of concerns, allows teams to work independently and enables each application to have its own release cadence and CI/CD pipeline. For the purposes of this tech test, the projects were kept together to simplify the reviewer experience, making it easier to understand the overall solution and run the application with minimal setup.

### Testing

For the backend, I used xUnit to create unit tests covering the individual calculation implementations, ensuring that the core business logic produces the expected results. I also used WebApplicationFactory to write integration tests against the API, validating scenarios such as successful requests, validation failures, invalid request payloads and unknown calculations. This provides confidence that the API behaves correctly as a whole, including its routing, deserialisation and validation behaviour.

For the frontend, I chose to use Vitest, as it integrates well with Vite and provides first-class support for TypeScript, which was used to build the React application. Frontend tests focus on validating component behaviour and user interactions, such as rendering dynamic form fields, displaying validation messages and presenting calculation results correctly.

### Patterns used

- Stratergy to allow one abstraction to represent any calculation
- Template to define that when running a calculation it must validate it first before running the logic
- Factory to get the correct calculation from the list of registered calculations

## Adding a New Calculation

To add a new calculation to the backend:

- Create a new class that inherits from the abstract Calculations.Calculation base class.
- Create a request model and response model for the calculation.
- Add validation and display attributes to the request model. These are used both for backend validation and for generating frontend form metadata.
- Implement the calculation and validation logic in the new calculation class.
- Register the new calculation with dependency injection in Program.cs.

Once registered, the calculation becomes available through the API. The frontend can then discover it from the calculation metadata endpoint and dynamically render the required form fields.
