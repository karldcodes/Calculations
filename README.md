# Calculations

## Endpoints

The API exposes a generic calculation execution endpoint:

`POST /calculations/{name}`

The shape of the request body depends on the selected calculation. Rather than manually maintaining separate OpenAPI definitions for each calculation, the API exposes a metadata endpoint.

`GET /calculations`

This endpoint returns the available calculations and their required request fields. The frontend uses this metadata to dynamically render the form. This keeps the backend as the source of truth and avoids duplicating calculation-specific contracts in both OpenAPI and frontend code.

`GET /swagger`

Interactive API documentation via Swagger UI when ran locally

`GET /health`

Health check URL for container orchestration platforms such as AKS.

## Architecture Summary

The solution was designed to minimise duplication between the frontend and backend by making the backend request models the single source of truth for calculations, validation rules and form definitions.

The backend is implemented as a minimal ASP.NET Core API using a strategy pattern to support multiple calculations. Each calculation implements a shared abstraction and is registered through dependency injection. A calculation factory resolves the appropriate implementation at runtime based on the calculation selected by the user.

Each calculation defines its own request and response models. The request models are decorated with Data Annotation attributes such as Required, Range and Display. These attributes serve multiple purposes:

- Defining the API contract used during deserialisation.
- Providing server-side validation rules.
- Supplying metadata used to generate the frontend forms.

At application startup, the API reflects over the registered calculations and generates a cached collection of calculation metadata. This metadata includes information such as field names, labels, input types and validation hints. The frontend retrieves this metadata through the GET /calculations endpoint and uses it to dynamically construct the user interface.

The frontend is implemented using React, TypeScript and Tailwind CSS. Calculation definitions are retrieved using SWR, providing lightweight caching and preventing unnecessary repeated requests. Rather than maintaining a separate hard-coded form for each calculation, the UI renders inputs dynamically based on the metadata returned by the API. As a result, introducing a new calculation does not require any frontend changes.

When a form is submitted, the frontend serialises the input values into JSON and posts them to the relevant calculation endpoint. The backend deserialises the request into the strongly typed request model for the selected calculation and executes the calculation logic.

Validation is intentionally centralised on the backend to avoid maintaining duplicate validation rules in both applications. Validation failures are returned using ASP.NET Core's ValidationProblem response format, allowing the frontend to display field-level error messages alongside the relevant inputs, while also supporting generic form-level errors.

The API also includes OpenTelemetry instrumentation for logs, traces and metrics, together with CORS configuration to support local development. Source-generated logging has been added around request processing to aid troubleshooting and demonstrate how operational concerns could be addressed in a production environment.

### Precision in calculations

As the API is performing calculations I chose to use the decimal type for my models properties as this offers the highest level of precision. Any returned results are also not rounded.

### Containerization

For this tech test I used docker compose to keep things simple rather then a full blown kubernetes implementation. The compose file builds the API and frontend using the docker file in the corresponding projects. It also provisions Gragana's LGTM stack to demonstrate how logs, metrics and traces generated by the application to be viewed and explored through a single observability platform.

### Future development and enhancements (Cloud & DevOps)

As the application is already containerized this makes it easy to move it into a cloud orchestrator. If it was going to be released as it is then a simple setup of using Azure App Service or Azure Container Apps would be enough. As adding kubernetes adds additional complexity in managing manifests and cost etc.

However as the inital requirements mention uptime and responsiveness across mulitple regions and mentioned about extending with additional APIs a setup similar to below could be used as a starting point:

#### Infastructure

```
Azure Front Door -> Azure Kubernetes Service -> Calculation APIs/Frontend pods

Application insights 

```

**Azure front door**

I would use this to provide a single public entry point for the application. It would route users to the nearest healthy AKS deployment based on their geographic location. This helps reduce latency and improve responsiveness for a global user base. It also provides resilience and high availability by routing fail over traffic to the next available region.

Lastly it provides other useful services such as Web Application Firewall (WAF) that helps defend against common web attacks before requests reach the rest of the application.

**Azure Kubernetes Service**

I would use AKS to orchestrate the application as it provides auto scaling, rolling deployments, service discovery and multi-zone deployments. This would allow the architecture to evolve as demand increases without requiring a significant redesign.

**Application insights**

I would use this platform as it provides a central location for logs, traces and metrics. Its also managed completely by microsoft so that saves any operational overhead and provides native intergration with the other Azure products we are already using.

#### CI/CD Pipeline

To work with the infastructure outlined above I would setup a CI/CD pipeline in Azure devops. I would choose Azure devops as they support yaml based pipelines which can be version controlled and it keeps everything under the Azure ecosystem which improves compability and ease of setup.

The finished artifact of a pipeline would be a new docker image. This would be stored in the Azure container registry ready to be deployed into AKS.

For the pipeline I would set conditions so that it would run on a feature branch and the other on a pull request. I'd also setup manual approval on production releases.

**Backend pipeline**

For feature branches and pull requests, the pipeline would:

- Restore NuGet packages.
- Run code quality and security checks.
- Build the API in Release mode.
- Run unit and integration tests.
- Fail the pipeline if any checks do not pass.

For pull requests or approved merges into a deployable branch, the pipeline would then:

- Build the API Docker image.
- Tag the image using the release version.
- Push the image to Azure Container Registry.
- Publish or apply the Kubernetes manifests.
- Deploy the image to AKS using a rolling deployment.
- Run smoke tests
- Roll back or block promotion if health checks or smoke tests fail.

**Frontend pipeline**

For feature branches and pull requests, the pipeline would:

- Install frontend dependencies using `npm ci`. (uses dependency versions from the package-lock.json file)
- Run code quality, linting and security checks.
- Run frontend unit tests.
- Build the Vite application to produce a production-ready bundle.
- Fail the pipeline if any checks do not pass.

For pull requests or approved merges into a deployable branch, the pipeline would then:

- Build the frontend Docker image.
- Tag the image using the release version.
- Push the image to Azure Container Registry.
- Publish or apply the Kubernetes manifests.
- Deploy the image to AKS using a rolling deployment.
- Run smoke tests
- Roll back or block promotion if deployment validation fails.

### Trade offs

While I wanted the backend to be the source of truth it does add additional complexities and currently has limitations in what can be configured. For example if you wanted to add additional properties to the frontend form inputs they have to be added to the validation model as attributes. I would change this so that there was a configuration model that allowed you to set your own data and then this would be sent to the frontend instead e.g

```
var field = new FormInput {
    Name = "Probability A",
    Type = "number"
    ...
}
```

Or with further additional changes a configuration object could be created and stored in a nosql database and have a UI over it so the user could configure their own calculation settings. The calculation logic could also be configured dynamically and run using maybe antlr etc

Its also worth noting here that in a real application I would have the frontend in a seperate solution rather then combined with the backend as we have here. This would seperate concerns and allow for independant development by different teams. The two were combined in this case so its easier for the reviewer to see what was done and run the application with one click.

### Patterns used

- Stratergy to allow one abstraction to represent any calculation
- Template to define that when running a calculation it must validate it first before running the logic
- Factory to get the correct calculation from the list of registered calculations

## Adding a New Calculation

To add a new calculation to the backend:

- Create a new class that inherits from the abstract Calculations.Calculation base class.
- Create a request model and response model for the calculation.
- Add validation and display attributes to the request model. These are used both for backend validation and for generating frontend form metadata.
- Implement the calculation and validation logic in the new calculation class.
- Register the new calculation with dependency injection in Program.cs.

Once registered, the calculation becomes available through the API. The frontend can then discover it from the calculation metadata endpoint and dynamically render the required form fields.
